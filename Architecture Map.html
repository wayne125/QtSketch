The re-entry loop: when IndigoService finishes a job (e.g. layoutFinished), MainWindow.qml's Connections block calls activeCanvas.loadMolfile(...) — which re-enters the V8Process → worker path above. Indigo never holds state; every result gets funneled back into the worker's _struct as the one source of truth.

Engine migration (2026-07-10): the worker transport was originally a spawned Node.js child process talking newline-delimited JSON over stdin/stdout (QProcess). That's been fully replaced with QjsEngine, an in-process QuickJS-ng JSRuntime/JSContext per document — V8Process::sendCommand's public shape is unchanged, only its internals differ (direct JS_Call instead of a pipe write). This removed the "Node.js must be on PATH or bundled next to the binary" deployment requirement entirely. V8 was evaluated and passed over: MSVC (needed for V8 anyway) is now available, but V8's build system (depot_tools/GN/Ninja, no CMake integration, a 10-20GB checkout, hours-long builds) was judged not worth it since this app's actual bottleneck was IPC overhead, not JS execution speed.

Argument marshaling gotcha (found post-migration): QjsEngine::variantToJs (src/qjs_engine.cpp) converts each QVariant in sendCommand's args list into a real JS value. It handles scalars directly, and QVariantList/QVariantMap recursively into real JS arrays/objects — the latter case was originally missing, which silently broke every TEMPLATE_* ring tool (addRing's coords argument is a QVariantList) while scalar-only commands kept working. scripts/worker_smoke_test.js never would have caught this — it drives the worker via the Node fallback path, never through QjsEngine. A manual in-app test is the only real verification for this seam; there's no automated test exercising the QjsEngine transport itself yet.

Verification pass (2026-07-10): a systematic bug-hunt across the whole project after the migration found and fixed 9 issues — a deferred-error-signal bug in V8Process, a cross-thread QPointer race across all 20 QtConcurrent call sites in IndigoService.cpp (see the Indigo seam's step 1 below), two undo/redo asymmetries in v8_worker.js's sgroup/functional-group handling, and four QML bugs including a recurring pattern worth remembering: several call sites forgot to resolve a contracted sgroup pill id to a real atom id before touching the backend (the established fix is ChemCanvas.qml's own resolveHitAtom() helper — check any new atom-targeting code path against it).

Canvas interaction tools (2026-07-11): added a HAND (pan) tool, a SELECT_LASSO tool, a hard page/canvas boundary, and — replacing an initial standalone ROTATE tool the same day — PowerPoint-style selection handles (4 corner + 4 side resize, 1 rotate) that appear automatically on any qualifying selection while SELECT/SELECT_FRAGMENT is active. See calm-launching-kettle.md for the full ChemDraw/PowerPoint research. Notable patterns: rotateSelectionLive/commitRotate and the new scaleSelectionLive/commitScale were generalized to every selectable type (atoms, reaction arrows, rxn-plus signs, multitail arrows) via shared _snapshotSelectionPoints/_writeSelectionPoint helpers mirroring moveSelection's own multi-type handling — a single arrow or a mixed molecule+arrow+text selection now rotates/resizes as a whole; resize scales uniformly about the handle's opposite point (not the centroid, unlike rotate), since anisotropic stretch would distort bond lengths; selectByLasso reuses selectByRect's structure but is not a drop-in copy — ChemDraw's lasso only selects objects entirely enclosed by the path; the page boundary (PAGE_MIN_X/MAX_X/MIN_Y/MAX_Y) is a hard clamp by explicit user decision despite ChemDraw's own page lines being only a soft print guide, and is deliberately not applied to fusion-sensitive geometry to avoid misaligning a fused seam. Two operational findings from this pass: CMakeLists.txt's icon list is an explicit file list, not a glob — a new icon on disk isn't packaged until added there too (missed for hand.svg/select-lasso.svg initially); and Bash-launched GUI checks via PATH alone can silently fail with zero output (STATUS_DLL_NOT_FOUND) — real verification needs windeployqt.exe --qmldir <src> run once per build tree plus the matching MinGW runtime DLLs, checked via PowerShell's Start-Process exit code, not just an empty Bash log. Verified via a temporary Node harness, the standing smoke test, a clean MinGW build, and (this time) a real interactive launch with captured stderr showing zero QML errors beyond pre-existing benign style warnings; manual mouse-driven interaction and the MSVC build are still pending.

"Load from InChI" (2026-07-11) — and why not InChIKey: follow-up prompted by a request to "load molecules from InChIKey" — confirmed with the user before building anything that InChIKey is a one-way hash with no reverse algorithm, so the real request was either loading from the full InChI string (invertible) or resolving an InChIKey via an external database like PubChem (network-dependent, never done in this app, remains unbuilt). Built the first. Key discovery: Indigo's generic loader (indigoLoadMoleculeFromString, the same one "Load from SMILES" already calls via IndigoService::layout()) auto-detects and parses InChI natively — confirmed via a standalone test that this works even without indigo-inchi.dll linked or indigoInchiInit called at all. The plugin (linked above) is only needed for generating an InChI from a structure, not loading one. So this needed zero new backend code — purely a new "Load from InChI" toolbar entry + dialog in MainWindow.qml, mirroring smilesDialog exactly, calling the same indigoSvc.layout(text). Added a live inline warning (regex-matches the InChIKey shape) in the dialog, directly targeting the mix-up that prompted this feature. Verified via a standalone repro, the standing smoke test (unaffected), a clean MinGW build, and a real interactive launch with no new QML errors.

Reaction structure validation (2026-07-11): IndigoService::checkStructure had an explicit reaction guard returning a placeholder instead of ever checking anything. indigoCheckObj on a whole reaction handle isn't usable the same way as on a molecule — confirmed via a standalone test before writing any real code: it returns an empty-string key with no component association, which the existing regex-based JSON parser can't classify. Fix: iterate indigoIterateReactants/indigoIterateProducts and run indigoCheckObj on each component individually — gives back the exact same clean per-type shape the molecule branch already parses, just with ids local to that component; the shared parsing logic was factored into a file-local parseCheckReport() so both branches use the same code. Deliberate scope boundary: this only produces a text report — inline badge/red-bond highlighting stays off for reactions, since mapping per-component-local ids back to global canvas ids would need matching MolSerializer's own fragment-ordering when serializing a $RXN string, not safely verifiable without disproportionate effort into third-party bundled code, and a wrong mapping would silently highlight the wrong atom — worse than the stub it replaces. Verified via a standalone test against both a broken reaction (genuine valence error) and a clean one, the standing smoke test (unaffected), a clean MinGW build, and a real interactive launch with no new QML errors.

loadMolfile data loss on the Indigo round-trip (2026-07-11): started from "how do we minimize worker↔Indigo IPC overhead" — investigating found the actual overhead negligible (MDL parsing at this app's sizes is microsecond-scale, dwarfed by the thread-hop/debounce timers already in place) but surfaced a real correctness bug instead. MDL molfile/RXN — what Layout/Aromatize/Dearomatize/Normalize/Standardize all round-trip through — has no concept of Ketcher's own text annotations or multitail arrows. loadMolfile() did a full _struct = loaded replace with whatever came back, so both were silently deleted on every one of those five actions (reaction arrows/plus signs were fine — $RXN is a real MDL concept). Confirmed via direct calls to getStructure("mol", ...) before writing any fix. Fix: merge the outgoing struct's texts/multitailArrows pools into the freshly-deserialized one inside loadMolfile() itself — safe because that function is only ever called for "reload a modified version of the same document" (those five ops, plus biopolymer expansion); genuine file open goes through the separate loadStructure() path, confirmed by tracing MainWindow.qml's loadFromFile(). Found in passing, fixed as a same-day follow-up (see next note): getStructure("ket", ...) threw/returned empty specifically when a multitail arrow was present, even though KET otherwise preserves both texts and multitail arrows correctly. Verified via a disposable Node harness simulating the round-trip against the real worker, the standing smoke test (unaffected), a clean MinGW build, and a real interactive launch with no new QML errors.

KET multitail-arrow crash (2026-07-11): same-day follow-up. Root-caused, not guessed: patched a disposable copy of src/v8_worker.js (in /tmp, tracked file never touched) so getStructure's catch block would stop silently swallowing the exception, then reran the exact repro. Real error: TypeError: multitailArrow.toKetNode is not a function, thrown inside KetSerializer.serializeMicromolecules (chem-core.js, vendored) — it walks struct.multitailArrows directly and calls .toKetNode() on each entry, assuming a real chem-core MultitailArrow class instance. This app's own multitail arrows (_makeMultitailArrow) are plain data objects with no such method — already flagged in the Part B audit ("Sketch reimplemented this as plain objects"). The crash happens before _injectMultitailArrows (which correctly builds KET nodes from the plain-object data — never the actual bug) gets a chance to run. Second call site with the identical problem: getClipboardAsKet() had the same crash risk and separately never called _injectMultitailArrows at all. Fix: a new _serializeMicromoleculesSafe(struct) helper — mirroring the existing _reattachMultitailArrows's established pattern of swapping in new CoreLib.ChemCore.Pool() — temporarily empties struct.multitailArrows for just the serializeMicromolecules call, restoring it right after in a finally; safe because both call sites already re-inject the correct nodes afterward from the real pool data. Vendored chem-core.js was not touched. Pattern worth repeating: when a caught exception is suspiciously silent, patch a disposable copy to unmask it rather than guessing from the symptom alone — the second bug this session (after the InChIKey buffer-aliasing bug) found this way. Verified via the exact repro: both call sites now return non-empty KET JSON containing the multitail-arrow node; standing smoke test unaffected, clean MinGW build, real interactive launch with no new QML errors.

Two integration seams

Every backlog item is chemistry-model work (touches _struct, wants undo/redo, needs to render) or toolkit work (a computed result handed back once) — never both. That split is exactly the chem-core.js / Indigo divide, and it decides which files a new feature touches.

① The worker seam

For anything built on an unused chem-core.js export — biopolymer drawing, image embedding, native multitail arrows, R-group attachment helpers.

  1. Add the operation to src/v8_worker.js, calling the already-loaded CoreLib.ChemCore.X — follow the addText/addChain shape (build the object, wrap the mutation in makeCmd, call executeCommand)
  2. Register the new cmd string in the if/else dispatch inside _dispatchCommand (src/v8_worker.js:4026)
  3. Add a matching Q_INVOKABLE to v8_process.h/.cpp that calls sendCommand(...) — array/object-shaped arguments are fine (QjsEngine::variantToJs converts QVariantList/QVariantMap recursively into real JS arrays/objects, e.g. addRing's coords list), not just scalars
  4. Extend buildRenderPrimitives if the new entity needs to reach the canvas, then teach MoleculeLayer/LabelLayer/SelectionLayer to draw and hit-test it
  5. Add the tool/menu entry in ToolPanel.qml or MainWindow.qml, reusing IconCell/AnchoredPicker/TaskDialog

② The Indigo seam

For anything built on an unused Indigo C function — similarity search, SMARTS matching, InChI, native rendering, SDF/RDF batch browsing, scaffold decomposition, reaction enumeration, auto-AAM/pKa.

  1. Add a method to IndigoService.h/.cpp following the existing layout()/calcProperties() shape — QtConcurrent::run, own indigoAllocSessionId(), then emitOnGuiThread(self, [...](IndigoService *s) { emit s->xyzFinished(...); }) to emit the result — not a raw if (self) emit self->... from the background thread. QPointer's guard isn't thread-safe for a concurrent check-then-use; emitOnGuiThread posts the check-and-emit onto the GUI thread instead, serialized against ~IndigoService() by the same event loop (found and fixed across all 20 existing call sites in the 2026-07-10 verification pass — this is now the required pattern)
  2. Wire a handler in MainWindow.qml's Connections { target: indigoSvc } block
  3. Feed the result back to the model either via activeCanvas.loadMolfile(...) (structural result) or straight into a QML panel (a computed value, e.g. a similarity score or InChIKey string)
  4. This path never touches v8_worker.js — the worker is the passive supplier of the molfile string Indigo is handed

③ The Bingo seam (new — not wired in at all yet)

For similarity search, substructure search, exact-match search, and formula search over a collection — the template library, or a user-opened SDF/RDF.

  1. Prerequisite, not yet done: link bingo-nosql.dll in CMakeLists.txt (mirroring the indigo.dll pattern — on MSVC this needs its own generated .lib, same dumpbin/lib.exe process already used for indigo.dll)
  2. Add a new BingoService (or extend IndigoService) following the same QtConcurrent::run + own-session shape
  3. Build the index once (e.g. over templates/library.sdf's 276 entries) via bingoCreateDatabaseFile/bingoInsertRecordObj, then query with bingoSearchSub/bingoSearchSim/bingoSearchExact/bingoSearchMolFormula
  4. Like the Indigo seam, this never touches v8_worker.js directly — results (a list of matching template names/ids) feed a QML popup, not the live _struct
